# CU-07: registro de comprador

## Decisiones e integración

Se mantiene una sola identidad en `user_accounts`. El registro crea COMPRADOR con estado ACTIVA y `email_verified_at` nulo, sin sesión autenticada ni tienda. La verificación, el reenvío, los tokens y la activación condicional de VENDEDOR siguen perteneciendo a CU-08/CU-12.

Los datos personales viven en `account_profiles`, separados de `UserAccount` y de los objetos serializados de sesión. El correo continúa en la identidad compartida. Las cuentas antiguas pueden no tener perfil: la migración no inventa datos ni acepta condiciones en su nombre. Esta estructura permite que CU-09 gestione posteriormente el mismo perfil.

La habilitación usa la identidad de sesión, valida estado y verificación, y añade únicamente una fila COMPRADOR mediante una inserción atómica y la clave primaria de roles. No guarda una copia completa de `UserAccount`, no modifica contraseña, perfil o verificación y no selecciona automáticamente un rol activo. Las solicitudes repetidas devuelven que la cuenta ya tiene COMPRADOR.

Los términos de comprador y privacidad son avisos académicos versionados en `BuyerTerms`, independientes de `SellerTerms`. Se conserva fecha y versión de ambas aceptaciones en `buyer_consents`.

El envío de verificación ocurre después de confirmar la transacción de cuenta, perfil, rol y aceptación. La espera completa del adaptador de correo está limitada a 10 segundos; ante excepción o vencimiento se conserva la cuenta pendiente. El SMTP normal mantiene la configuración TLS existente. La excepción de SMTP sin TLS se limita al simulador del entorno E2E desechable.

## API nueva

Todos los POST requieren la cookie y el encabezado CSRF obtenidos de `GET /api/auth/csrf`.

- `GET /api/buyers/terms`: público. Devuelve `termsVersion`, `terms`, `privacyVersion`, `privacy`.
- `POST /api/buyers/register`: público. Devuelve 201 con `emailVerificationRequired`, `verificationDeliveryFailed`, `message`.
- `POST /api/buyers/enable`: autenticado. Devuelve 200 con `buyerRoleAdded`, `message`. No acepta identidad ni roles arbitrarios en el cuerpo.

Ejemplo de alta, con datos exclusivamente ficticios:

```json
{
  "fullName": "Ana Pérez",
  "birthDate": "2000-05-20",
  "email": "ana@example.test",
  "phone": "+57 300 123 4567",
  "password": "ExampleTestPassword123!",
  "passwordConfirmation": "ExampleTestPassword123!",
  "acceptTerms": true,
  "acceptPrivacy": true
}
```

Habilitación:

```json
{"acceptTerms": true, "acceptPrivacy": true}
```

El correo se normaliza eliminando espacios externos y pasando a minúsculas. Nombre: obligatorio, máximo 150 caracteres. Fecha: obligatoria y no futura, sin edad mínima. Teléfono: máximo 32 caracteres, prefijo + opcional, dígitos y separadores habituales. Contraseña: política compartida de mínimo 12 puntos de código y máximo 72 bytes UTF-8; confirmación igual. Las dos aceptaciones son obligatorias.

Errores: 400 para validación, confirmación distinta o campos desconocidos; 401 sin autenticación en habilitación; 403 para CSRF o cuenta no disponible; 409 `ACCOUNT_ACCESS_REQUIRED` para alta que requiere utilizar una cuenta existente. La respuesta pública no enumera roles, perfil ni estado de verificación de otra cuenta. El fallo SMTP no convierte el alta persistida en error de creación: devuelve 201 con `verificationDeliveryFailed: true`.

Se reutilizan sin cambiar sus contratos:

- `POST /api/auth/email-verification/resend` con correo y contraseña.
- `POST /api/auth/email-verification/confirm` con token.
- `GET /api/auth/me` para refrescar roles visibles.
- `PUT /api/auth/active-role` para selección explícita del rol.

## Migración

`V45__buyer_profiles_and_consent.sql` añade `account_profiles` y `buyer_consents` con claves foráneas a la cuenta y unicidad por cuenta/versión. No altera migraciones previas, cuentas, pedidos ni sesiones. Flyway sigue siendo propietario del esquema.

## Comprobación y demostración local

Requisitos: Docker funcionando, dependencias de frontend instaladas y Chrome disponible para Playwright. No se necesita SMTP productivo ni una base local existente.

Prueba automatizada con navegador, backend real, MySQL y Mailpit:

```bash
bash scripts/cu07-real-e2e.sh
```

El script crea un proyecto Compose con nombre único, carga únicamente fixtures públicos de prueba y elimina sus contenedores al terminar. Ejecuta el registro real con correo, habilitación de comprador desde vendedor y regresión de login/logout de CU-08. No usa ni modifica el repositorio externo de pruebas.

Para una demostración manual desde la raíz:

```bash
CU08_E2E_PORT=14307 CU07_MAIL_PORT=18025 docker compose --env-file /dev/null -p cu07-demo -f compose.e2e.yaml -f compose.cu07-e2e.yaml up --build --wait
```

1. Abrir `http://127.0.0.1:14307` y pulsar **Crear cuenta de comprador / Habilitar COMPRADOR**.
2. Completar datos ficticios, contraseña y confirmación; leer y aceptar ambos avisos.
3. Crear la cuenta. La interfaz muestra el envío y el paso de verificación.
4. Abrir el buzón local `http://127.0.0.1:18025`. Copiar el código recibido a la interfaz, sin publicarlo en logs ni usar buzones reales.
5. Confirmar el correo. El panel se cierra y abre el inicio de sesión.
6. Iniciar sesión y comprobar COMPRADOR y acceso a Mis pedidos.
7. Para habilitar una cuenta existente, iniciar sesión con esa cuenta y abrir nuevamente el registro. La habilitación conserva el rol activo y permite volver al selector de roles de CU-08.

Limpieza exclusiva del proyecto de demostración:

```bash
docker compose --env-file /dev/null -p cu07-demo -f compose.e2e.yaml -f compose.cu07-e2e.yaml down --volumes --remove-orphans
```

Otros comandos de comprobación:

```bash
cd backend/demo
./mvnw verify
./mvnw -Dtest=BuyerRegistrationIntegrationTests,BuyerProfileMigrationTests test
```

```bash
cd frontend
npm run build
PLAYWRIGHT_PORT=14314 npx playwright test --project=chrome
PLAYWRIGHT_PORT=14315 npx playwright test --project=mobile e2e/registro-comprador.spec.ts
```

Las pruebas Java usan MySQL Testcontainers. Las pruebas de `frontend/e2e` simulan HTTP; las de `e2e-real` prueban el servidor real. No son intercambiables. Los resultados efectivos de la ejecución se registran en el informe de entrega, sin deducir éxito por la sola existencia de pruebas.

Las cifras anteriores corresponden a las ejecuciones finales correctas, no a los intentos intermedios fallidos o interrumpidos. El parser del buzón de pruebas admite códigos base64url que comienzan o terminan con guion.

No se ejecutó la prueba de rendimiento optativa de favoritos ni se probó SMTP productivo. Se usaron únicamente MySQL efímero y correo simulado. La entrega no incluye CU-09 ni cambios en el repositorio externo de pruebas. No se realizaron operaciones Git.
